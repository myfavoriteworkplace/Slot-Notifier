What Already Exists (Relevant to This Feature)
The schema already has OTP fields on the bookings table — they were built but never wired up:
* verificationCode — meant to store the OTP
* verificationStatus — currently always set to 'pending' (free booking) or 'confirmed' (paid booking), never actually used for OTP
* verificationExpiresAt — meant to store when the OTP expires, currently always null
A patients table already exists with name, email, phone, clinicId, doctorId — this is exactly the "soft account" the AI agent described. It exists but is currently not linked to the booking flow at all.
Resend email is fully set up with styled templates already — adding an OTP email is straightforward.
Current booking flow (no OTP today):
1. Patient fills name, phone, email → picks clinic, date, slot
2. Hits "Book" → booking is created immediately with verificationStatus: 'pending'
3. Clinic sees the booking and manually confirms
4. Or patient pays via Razorpay → booking auto-confirmed

What Needs to Be Built
Here's what I would add, in plain language:
1. New API endpoints (backend)
* POST /api/public/otp/send — patient enters their email → app generates a 6-digit OTP, stores it (hashed) with a 5-minute expiry against their email, sends the OTP email via Resend
* POST /api/public/otp/verify — patient enters the OTP → app checks it, marks email as verified, returns a short-lived token (a random string stored in the session or as a signed value)
* The existing booking endpoint (/api/public/bookings) would then require this verified token before creating a booking
2. Schema additions
* A new email_otps table — email, otpHash (hashed OTP, never stored plain), expiresAt, verified, createdAt. Kept separate from bookings so the OTP can be verified before the booking even exists
* The existing verificationCode/verificationStatus/verificationExpiresAt fields on bookings can be repurposed to record that the booking was created with a verified email
3. Frontend changes (Book.tsx)
* Add an OTP step between filling in details and submitting the booking
* After the patient enters their email, a "Verify Email" button sends the OTP
* A 6-digit OTP input appears → patient enters code → verified → then the "Book" / "Pay" button becomes active
* The demo clinic path (local mock) would bypass OTP
4. New OTP email template
* A clean styled email (matching existing templates) with the 6-digit code and a 5-minute validity notice
5. Soft patient record (optional, can be Phase 2)
* After a verified booking, upsert a record in the patients table using the email as the unique key — so returning patients are recognised
* This doesn't block the OTP feature and can be added after

What I Will NOT change
* No changes to clinic/doctor/admin auth — completely separate
* No changes to the Razorpay flow except that payment also requires prior OTP verification
* No forced account creation for patients — stays frictionless
* No changes to existing booking confirmation emails
